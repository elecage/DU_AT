지체장애인을 위한 IoT 기반 보호자 호출·확인 시스템
ESP32-C3 호출 단말, Raspberry Pi 5 서버 및 Telegram을 연계한 CareCall 연구 프로젝트

물리 버튼을 조작할 수 있는 지체장애인이 보호자에게 도움을 요청하고, 보호자의 확인 여부를 호출 단말의 LED로 전달받을 수 있도록 구현한 IoT 기반 호출·확인 시스템입니다.
본 프로젝트는 단순히 알림을 전송하는 데 그치지 않고, 통신 장애 중 호출 보존, 서버 저장 확인, 중복 호출 처리, 최신 호출 검증 및 보호자 확인 결과 전달까지 하나의 시스템으로 구현하는 것을 목표로 합니다.
1. 시스템 설계 시 고려사항
- 사용자가 도움을 요청했더라도 네트워크 장애가 발생하면 호출이 유실될 수 있습니다.
- 알림이 보호자에게 전송됐는지만으로는 사용자가 보호자의 확인 여부를 알기 어렵습니다.
- MQTT QoS 1은 전달 신뢰성을 높일 수 있지만 같은 메시지가 중복 도착할 가능성이 있습니다.
- 여러 위치에 호출 버튼을 설치하면 장치별 호출을 하나의 사용자 또는 장소 단위로 관리해야 합니다.
- 설치 장소가 변경될 때마다 개발자가 장치를 다시 연결하지 않아도 Wi-Fi를 변경할 수 있어야 합니다.
CareCall은 위 사항을 반영하여 호출 생성부터 보호자 확인까지의 전체 상태를 관리하도록 설계했습니다.
2. 연구 대상 및 연구 목표
연구 대상
- 물리 버튼을 직접 누를 수 있는 지체장애인
- 한 사용자가 침대, 책상, 화장실 등 여러 위치에서 보호자를 호출해야 하는 환경
- 여러 보호자가 동일 사용자의 호출을 함께 확인하는 환경
연구 목표
- 통신 장애 중에도 호출이 사라지지 않도록 보존
- Raspberry Pi에 정상 저장된 호출만 처리
- MQTT 재전송으로 발생하는 중복 호출 방지
- 최신 호출에 대해서만 보호자 확인 허용
- 보호자 확인 결과를 호출 단말 LED로 전달
- 여러 호출 버튼을 하나의 사용자·장소 단위로 통합 관리
- 휴대전화로 Pi와 호출 단말의 Wi-Fi 변경 지원

4. 전체 동작 과정
1. 사용자가 호출 버튼을 누릅니다.
2. ESP32-C3가 호출 정보를 내부 비휘발성 저장공간에 먼저 기록하고 LED를 켭니다.
3. 저장된 호출을 MQTT QoS 1로 Raspberry Pi에 전송합니다.
4. Raspberry Pi가 고유 이벤트 식별자로 중복 여부를 확인합니다.
5. 정상 호출을 SQLite에 저장하고 장치에 저장 완료 응답을 보냅니다.
6. ESP32-C3는 저장 완료 응답을 받은 호출만 내부 저장공간에서 제거합니다.
7. Telegram Bot이 등록된 보호자에게 호출 알림을 보냅니다.
8. 보호자 한 명이 최신 알림의 확인했습니다 버튼을 누릅니다.
9. Raspberry Pi가 최신 호출인지 다시 확인한 뒤 해당 호출 단말에 확인 결과를 전달합니다.
10. ESP32-C3의 LED가 꺼지면서 보호자 확인 완료를 사용자에게 알립니다.
5. 호출 상태와 LED 의미
상태	LED	의미
평상시	꺼짐	처리 중인 호출 없음
호출 발생	켜짐	호출이 생성되어 보호자 확인을 기다리는 상태
서버 저장 완료	켜짐 유지	호출은 안전하게 저장됐지만 보호자 확인은 아직 완료되지 않음

서버의 저장 완료와 보호자의 확인 완료는 서로 다른 상태로 관리합니다. 따라서 서버에 호출이 저장됐다는 이유만으로 LED가 꺼지지 않습니다.
6. 핵심 구현 기능
6.1 오프라인 호출 보존
- 호출을 전송하기 전에 ESP32-C3의 NVS에 저장합니다.
- NVS는 전원이 꺼져도 내용이 유지되는 내부 비휘발성 저장공간입니다.
- Wi-Fi 또는 Raspberry Pi 연결이 끊기면 호출을 삭제하지 않고 보관합니다.
- 통신이 복구되면 저장된 호출을 자동으로 다시 전송합니다.
- Raspberry Pi의 저장 완료 응답을 받은 호출만 NVS에서 제거합니다.
6.2 MQTT 중복 호출 처리
- 호출 전송에는 MQTT QoS 1을 사용합니다.
- QoS 1은 메시지를 최소 한 번 전달하지만 같은 호출이 다시 도착할 수 있습니다.
- 각 호출에 고유한 event_id를 부여해 재전송된 메시지를 동일 호출로 처리합니다.
- 이벤트 ID는 장치 ID, 칩 고유값 및 호출 순번을 조합해 생성합니다.
6.3 최신 호출 확인
- 보호자는 Telegram 알림의 확인했습니다 버튼으로 호출을 확인합니다.
- 같은 사용자에게 여러 호출이 발생하면 가장 최근 호출만 유효하게 처리합니다.
- 새 호출 알림이 생성되면 이전 메시지의 확인 버튼을 제거합니다.
- 늦게 도착한 이전 호출의 확인이 최신 호출의 LED를 끄지 못하도록 검증합니다.
6.4 다중 보호자
- 한 호출을 여러 보호자에게 전달할 수 있습니다.
- 보호자 중 한 명이 최신 호출을 정상적으로 확인하면 확인 완료로 처리합니다.
- 확인 결과는 같은 호출을 보고 있는 보호자와 해당 호출 단말에 반영됩니다.
6.5 다중 호출 버튼
- 한 대의 Raspberry Pi에 여러 ESP32-C3 호출 단말을 연결할 수 있습니다.
- 각 단말은 고유한 장치 ID와 MQTT 접속 정보를 사용합니다.
- 같은 사용자 또는 장소에 속한 장치는 동일한 set_id로 묶습니다.
- 어느 위치의 버튼을 누르더라도 같은 보호자 그룹으로 알림을 전달합니다.
- 호출 기록에는 실제로 눌린 장치를 구분할 수 있는 고유 정보가 유지됩니다.
6.6 현장 Wi-Fi 변경
- Raspberry Pi와 ESP32-C3가 각각 임시 설정용 Wi-Fi를 생성할 수 있습니다.
- 사용자는 휴대전화로 설정용 Wi-Fi에 접속해 현장 공유기의 정보를 입력합니다.
- 설정이 완료되면 장치는 정상 Wi-Fi 모드로 전환되고 설정용 Wi-Fi는 종료됩니다.
- 모니터, 키보드 또는 유선 LAN 없이도 설치 장소의 Wi-Fi를 변경할 수 있도록 구성했습니다.

10. 개인정보와 보안 고려사항
- Raspberry Pi에는 호출 처리에 필요한 최소 정보만 저장하도록 구성합니다.
- 실제 사용자, 보호자, 호출 기록 및 장치 자산 정보는 공개 소스와 분리합니다.
- Wi-Fi 비밀번호, MQTT 비밀번호 및 Telegram Bot Token은 소스 코드에 포함하지 않습니다.
- MQTT 익명 접속을 차단하고 장치별 계정과 최소 권한을 사용합니다.
- 장치는 자신의 호출 Topic과 응답 Topic에만 접근하도록 권한을 구분합니다.
- Telegram 등록은 운영자 승인과 보호자 초대 절차를 거쳐 처리합니다.
- 로그에는 비밀번호, Token 및 Chat ID 전체값을 출력하지 않습니다.

12. 연구의 특징
- 호출 전송뿐 아니라 보호자의 확인 결과까지 사용자에게 되돌려주는 양방향 구조입니다.
- ESP32-C3, Raspberry Pi 및 Telegram을 연계해 별도의 전용 보호자 앱 없이 구현했습니다.
- 호출을 장치와 서버에 단계적으로 보존해 통신 장애 상황의 호출 유실 가능성을 줄였습니다.
- 서버 저장 완료와 보호자 확인 완료를 분리해 호출 처리 상태를 명확하게 관리합니다.
- 고유 이벤트 식별자를 이용해 MQTT QoS 1의 중복 전달 문제를 처리했습니다.
- 여러 호출 위치를 하나의 사용자·장소 단위로 묶으면서 실제 호출 장치는 구분할 수 있습니다.
- 설치 장소가 바뀌어도 휴대전화로 Wi-Fi를 변경할 수 있도록 현장 운용성을 고려했습니다.
13. 현재 범위와 향후 과제
- 현재는 ESP32-C3 호출 단말 3대와 Raspberry Pi 5 한 대의 종단 간 동작을 검증했습니다.
- 첫 전시 환경에서는 약 5대의 호출 단말 구성을 예상하고 있습니다.
- 최대 20대 규모는 예상 확장 범위이며 동시 호출, 장시간 운용 및 네트워크 부하 시험이 추가로 필요합니다.
- button04 이후 신규 단말은 실제 회로 연결 후 추가 검증할 예정입니다.
- LED 링의 실제 소비 전류와 배터리 사용 시간은 완성 하드웨어 기준으로 측정해야 합니다.
- 완전히 새로운 Raspberry Pi 저장장치에서의 통합 OS 설치·복구 절차를 최종 검증해야 합니다.
- 실제 사용 환경을 고려한 장기 안정성, 보안 및 장애 복구 시험이 필요합니다.
